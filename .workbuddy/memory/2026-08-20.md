### 同步删除"复活"bug 修复（用户报：life 上已删任务同步后仍在）
- **现象**：用户重建 workspace-server docker（含上轮 tombstone 修复）后，本地 `npm run dev`；发现 life.hchch.tech 上有些待办在 quest 里已删，同步后仍存在于云端。
- **根因**（历史遗留态，非纯代码 bug）：
  1. 上轮 tombstone 修复**之前**的旧云代码忽略 `deletedTaskIds` → 早先删除的任务本地记了 `deletedTaskIds`、旧云不删；同步"成功"后本地 `clearAfterSync` 把 `deletedTaskIds` 清空。
  2. 旧云把那行经 `allQg` 拉回，前端 `mergeRemoteTasks` 把它**重新加回本地 quest** → 任务在两端同时"复活"，且本地已忘掉删除意图。
  3. 用户部署的新云代码能正确传播删除，但这些已复活的任务仍在两端，需再删一次才消失。
- **代码修复（云端 workspace-server `server/routes/tasks.cjs` POST /sync）**：新增"按本地快照对账删除"——事务内算出本次推送的 `pushedIds`，删除云端存在但 `pushedIds` 不含、且不在 `deletedTaskIds` 中的 `source='qg'` 行。语义=本地权威，删除**永远**能传播、杜绝复活；加 `pushedIds.size>0` 守卫防空快照误删全部。`node --check` 通过；临时 temp-DB 端到端测试 5/5 通过（对账删/经典 deletedTaskIds/防误删/空快照守卫）。
- **用户侧动作**：① 重新 build+启动 docker（让对账修复上线）；② 在 quest 里把那些"复活"的待办**再删一次**然后同步，它们会从云端永久消失、且不再回来；③ 今后任意本地删除都会自动上云。本地 quest 代码无需改（dev 已含 mergeRemoteTasks/markTaskDeleted）。
- **架构结论**：B+ 同步删除语义 = 本地权威 + 全量快照对账（删除行）+ 墓碑（云端→本地删除下传）。`deletedTaskIds` 队列与快照对账双保险。

### workspace-server Dockerfile 加固（better-sqlite3 原生编译）
- **用户报告**：原 `FROM node:22-slim` 镜像构建时报错 `better-sqlite3` 编译失败：`prebuild-install warn install Request timed out` → 退到 `node-gyp rebuild --release` → 需要 Python 但镜像里没有。这是任何"node-slim + 原生 C++ 模块（better-sqlite3 / bcrypt / canvas / sharp）"的经典坑。
- **加固版 Dockerfile**（`E:\PersonalFiles\Coding\workspace-server\Dockerfile`）：
  - 基镜像：`node:22-bookworm-slim`（与原 `node:22-slim` 实际等价，`slim` 默认就是 bookworm-slim；显式写出更清晰）。
  - 装原生编译依赖：`apt-get install --no-install-recommends python3 build-essential ca-certificates`。`build-essential` = gcc + g++ + make，单包搞定；`ca-certificates` 让 prebuild-install 能正常校验 GitHub releases 上下载的 prebuilt 二进制。
  - npm 噪声/超时优化：`NPM_CONFIG_FETCH_RETRIES=5 NPM_CONFIG_FETCH_TIMEOUT=600000 FUND=false AUDIT=false`（10 分钟超时 + 5 次重试，吃得下网络抖动）。
  - 安装方式：`npm ci --omit=dev`（有 lockfile，速度与确定性都更好；替代 `npm install --production`）。
  - 保留分层缓存：先 COPY `package.json package-lock.json` 再 npm ci，源码变更不会触发依赖重装。
- **复用场景**：任何 Node 项目用 `*-slim` 镜像 + 含 native deps 时，套这个模板即可。

### 关键发现：workspace「悬赏任务」里那 8 条 task 的真实来源
- **现象**：用户打开 quest 本地 `localStorage.__quest_guild_tasks`，里面有一堆 `ep_ms87...` / `dy_mszg...` 前缀的任务，如「完善代码并修复已知问题」「编写单元测试」「执行打包并验证产物」「读完《数学要素》」等。用户此前以为这些在 workspace 云端，且本地 quest 没有。
- **来源**：`scripts/ai-decompose.mjs` 用 LLM 拆解目标时生成的任务（`genId('ep')` 给史诗、`genId('dy')` 给每日）。snapshot 中 `source:'qg'` 硬编码。
- **为什么本地会有**：如果生成时加了 `--push` 直接上云，之后用户在 quest 点「同步」拉回了它们；也可能先生成 `generated-tasks.json`，再经 `import-tasks.mjs --push` 上云。无论哪条路，它们都是 quest 本地任务库的一部分，会被当作 qg 任务同步到云端 `workspace_tasks`。
- **为什么用户之前查云端 `source='qg'` 为 0**：大概率是查的时刻这些任务还没被 push，或云端 db 被重建过但本地还保留；下一次同步又会重新 push。
- **结论**：这些任务不是 workspace 原生任务，也不是 bug，而是 AI 拆解产物。若不需要，应在 quest 本地删除（会写墓碑/对账删除）再同步，云端才会真正清掉。

### 清理脚本 + 关键陷阱：应用与脚本共用同一 genId 格式
- **用户诉求**：写个清理脚本删掉 AI 拆解产生的任务；并问「会一直存在吗 / 删了有啥影响 / AI 拆解后还会再出现吗」。
- **关键陷阱（必须记）**：quest 应用自身的 `useTasks.ts:96 genId(prefix)` 与 `scripts/ai-decompose.mjs` / `import-tasks.mjs` 的 `genId` **格式完全相同**（`${prefix}_${Date.now().toString(36)}_${rand36}`），且应用创建史诗/每日也用 `ep`/`dy` 前缀（`useTasks.ts:364`）。因此 **不能靠 id 前缀区分"AI 产物"与"用户手建任务"**——只能靠 `source` 语义或让用户显式指定 id。
  - 数据流里 `source` 也会被同步抹平：应用创建=`'user'`，但经 `/sync` 推送时 `mapTask`（`sync/index.ts:47`）硬编码 `source:'qg'` 写进云端；拉回时 `mergeRemoteTasks` 云端独有分支**不设 source** → 本地变 `undefined`。所以本地 `source` 不可靠区分。
- **清理脚本** `scripts/clean-quest-localstorage.js`（浏览器控制台版，非 Node——数据在 localStorage）：
  - 默认 DRY RUN 列出全部任务（id/name/source/type/status），按 source 分布；
  - 配置 `APPLY` / `TARGET_IDS`（精确 id）/ `MATCH_NAME_RE`（名称正则）；
  - 真正删除时**同时**从 `__quest_guild_tasks` 移除 + 把 id 追加进 `__quest_guild_sync_v1.deletedTaskIds`，否则下次同步"对账删除"会把云端行又拉回来（删了又出现）；
  - 用法：F12 控制台粘贴 → 填 id/正则 → `APPLY=true` 再跑 → 刷新页面 → App 点「同步」让云端 workspace 清理。
- **三个问题答案**：① 会一直存在——它们是真实持久化任务，无过期机制，不删就永久留 localStorage 且每次同步推上云；② 删了几乎无系统影响（只是内容消失，已获声望/能力点是累计值不回扣，云端 qg 行经同步对账删除）；③ AI 拆解**会**再生成——这是脚本设计用途（把目标拆成任务），不是缓存 bug；不想进 quest 就不加 `--push` 先看 `generated-tasks.json`，或生成后不点同步，或直接用本脚本删。

### 设计反思：AI 拆解应走「草稿模式」而非直接落主任务库
- **用户洞察**：当前 AI 任务（脚本/按钮生成）直接进主任务库 `__quest_guild_tasks`，与正式任务无法区分、永久残留、清理靠控制台脚本、误删风险。用户提出正确方向：AI 拆解应先进「草稿」，可调整，确认后才进主任务库/上云；未确认则不应污染主列表。
- **改进方案（已绘制流程图确认）**：
  1. 新增独立「AI 草稿箱」存储键 `__quest_guild_ai_drafts`（独立于主任务库）。
  2. LLM 生成子任务 → 写入草稿箱（建议带 `ai-draft` tag/标记），前端「草稿面板」可预览/增删改/调难度。
  3. 用户「加入任务」→ 转正主任务库 + 标记待同步 + 移出草稿箱；「丢弃」或 7 天未处理 → 从草稿箱删除。
  4. 点「同步」时仅正式任务（主任务库）上云，草稿箱永不上云。
- **关键 UX 决策**：未确认的草稿**应跨会话保留（不 ephemeral 删除）**，避免误关页面丢失调整成果；只是不进主任务库、不污染、不会静默复活。可选 7 天自动过期作兜底。
- **前置依赖（Plan A 现实）**：App 内「AI 拆解」按钮当前在方案 A 下抛错（`src/api/tasks.ts:64` "AI 拆解需要后端 LLM 服务"）。要落地"App 内点 AI 拆解"，需改为浏览器侧直接调 LLM（读 `.env` 的 `AI_API_KEY`/`AI_BASE_URL`/`AI_MODEL`，OpenAI 兼容 `/chat/completions`，零依赖），不再依赖已下线的本地 server。
- **价值**：彻底消除"AI 任务混进正式任务"的混淆，清理/识别自动化（可加"清空 AI 草稿"按钮），与同步对账删除解耦。
